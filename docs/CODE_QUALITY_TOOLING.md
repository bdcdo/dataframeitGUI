# Stack de qualidade de código

Decision record da issue [#260](https://github.com/bdcdo/dataframeitGUI/issues/260) ("Avaliar complementos ao react-doctor"). Registra quais ferramentas de qualidade o projeto adotou, por que cada uma entrou (ou ficou de fora), o baseline de cada gate e como o débito legado é grandfathered. Complementa `docs/LINT_CONFIG.md`, que detalha especificamente o baseline do react-doctor, e `docs/VERIFICATION.md`, que trata da *estratégia* de verificação e das práticas contra a família de bugs "codificação não salva". A divisão é: aqui, quais gates existem e como disparam; lá, o que verificar e como.

## O problema

O react-doctor entende a semântica de React *dentro do arquivo* — `useEffect` desnecessário, estado derivado, prop drilling, acessibilidade. Por design, ele abriu mão da detecção de código morto (delegada ao knip) e não enxerga três eixos: o grafo do projeto (o que nenhuma ferramenta arquivo-a-arquivo vê), os tipos (regras de lint que precisam do type-checker) e o runtime. Some-se a isso que o backend Python não tinha nenhum gate de qualidade e que a única automação de segurança era o gitleaks (secrets). A #260 fechou essas lacunas montando uma stack em que cada peça cobre um eixo distinto, com uma exigência transversal: nenhum gate pode depender de o desenvolvedor lembrar de rodar algo na mão.

## O mapa — quem dispara o quê

A regra de ouro é que tudo roda sozinho, via git hook ou automação de servidor. Os hooks se instalam de uma vez com `pre-commit install` (o `default_install_hook_types` em `.pre-commit-config.yaml` cobre os dois estágios). A divisão entre os estágios segue o custo: o que é leve e por-arquivo roda a cada commit; o que carrega o grafo do projeto ou o programa de tipos roda só no push.

| Quem dispara | Quando | Ferramentas | Grandfathering |
|---|---|---|---|
| `pre-commit` | todo commit (leve, file-scoped) | gitleaks · ruff (lint+format) · actionlint · deploy notifier · react-doctor | só o arquivo/linha tocado é checado; o notifier roda quando seu workflow ou teste muda |
| `pre-push` | todo `git push` (pesado, grafo/tipos) | typecheck · vitest · e2e-smoke (Playwright) · lint:types · fallow audit · semgrep · backend-pytest · mypy · db-tests | new-only / file-scoped (ver cada um); Vitest, pytest e db-tests rodam as suítes inteiras; e2e-smoke e db-tests falham fechado no pre-push (envs E2E/Clerk faltando; Supabase local fora do ar, respectivamente) |
| GitHub Actions (`ci.yml`) | todo PR e push na `main` | os hooks de `pre-push`, uma célula por hook, e os de `pre-commit`, numa chamada só, menos os de `.github/ci-exempt-gates.json` · eslint · banco (`database-tests.yml`) | estado absoluto: cada hook roda com `--all-files` |
| GitHub (servidor) | automático | Dependabot | n/a — abre PRs de vuln sozinho |
| on-demand | ao investigar performance | React Scan | n/a — ferramenta de diagnóstico, não gate |

A única peça manual é o React Scan, e por natureza: ele é um overlay visual que precisa da aplicação rodando no browser, então não há o que amarrar a um hook de git.

## As ferramentas adotadas

### fallow — o grafo do codebase

`fallow` 3.3.0 (devDependency pinada). É a peça que preenche a lacuna estrutural que o react-doctor deixou: constrói o grafo de módulos do projeto inteiro para achar o que ferramentas arquivo-a-arquivo não veem — export que ninguém importa, arquivo que ninguém importa, dependência circular, bloco duplicado entre arquivos, dependência no `package.json` nunca importada. É, na prática, um `knip` + `jscpd` em Rust, sub-segundo. A camada estática é MIT; a camada de runtime (paga) não foi adotada.

> **Mudança de comportamento na 3.3:** o wrapper npm passou a **sair com código não-zero quando o binário morre por sinal**. Antes, um SIGSEGV ou um OOM kill era lido como exit 0 — o gate podia estar passando por crash silencioso. Se o `fallow audit` começar a falhar sem causa aparente, considere a hipótese de o crash já existir e só agora ser reportado.

O gate usa `fallow audit`, pelo `frontend/scripts/fallow-audit-gate.sh` no hook de pre-push (o `npm run fallow:audit` roda o audit cru, sem as guardas de versão e de config descritas abaixo e sem `--base`). O `audit` é purpose-built para PR quality gates: roda dead-code + complexidade + duplicação escopados aos arquivos alterados e retorna um verdict (pass/warn/fail), com exit 1 em fail. O modo default `--gate new-only` faz o grandfathering por design — só achados *introduzidos* pelo changeset afetam o verdict; os herdados são reportados com atribuição new-vs-inherited mas não barram. **Esse grandfathering vale para a severidade `warn`, não para regra que nós fixamos em `error`**: medido na 3.2.0 duas vezes, com `dead_code_introduced: 0` / `dead_code_inherited: 2`, a mesma regra em `warn` deu verdict `warn` e exit 0, e em `error` deu verdict `fail` e exit 1. Quem decide é o `dead_code_has_errors` do `summary` — a atribuição new-vs-inherited continua correta, ela só não é consultada quando há achado `error`. Isso contradiz a doc do fallow, que afirma que "inherited error-severity findings can be present in the JSON output while the verdict remains `pass`". Daí duas consequências práticas: **só se fixa em `error` regra cuja contagem de achados no projeto seja zero hoje** (confira com `npm run fallow`), e **para essas regras o gate é efetivamente global, não new-only** — um achado que chegue à `main` (via `SKIP=fallow-audit`, por exemplo) barra o push de todo mundo, não só de quem o introduziu. A saída de emergência, nesse caso, é `SKIP=fallow-audit git push` ou rebaixar a regra na config; o custo é assumido de propósito, ver abaixo. Gotcha registrado à parte: a flag global `--fail-on-issues` ("promotes `warn` to `error`") é **no-op** no `audit` — um `misplaced-directive` introduzido de propósito manteve verdict `warn` e exit 0 com e sem a flag. A doc do fallow só a descreve no comando `dead-code` e recomenda o sistema de `rules` para o resto, que é o caminho que usamos. O hook passa `--base origin/main`: sem ele, o fallow resolve a base pela merge-base contra o upstream da branch, e numa branch já pushada isso mediria só o delta desde o último push (o porquê completo está no comentário do hook em `.pre-commit-config.yaml`). O scan completo (`npm run fallow`, dead-code + dupes + health juntos) fica para inspeção manual.

Para atribuir new-vs-inherited, o `--gate new-only` cria um worktree do commit-base em `/tmp` (`fallow-audit-base-cache-<hash-config>-<base>`, detached HEAD) e o mantém como cache reutilizável entre pushes — evita refazer o `git worktree add` da árvore-base contra a mesma base. O `node_modules` do cache é um symlink para o `node_modules` vivo (não há cópia nem reinstalação), então cada cache tem ~8,5 MB e um miss custa só o checkout da fonte-base. O GC mede a idade **desde a criação** do cache (um cache-hit *não* atualiza o `.last-used`, então mesmo uma base em uso ativo contínuo é varrida ao vencer o TTL), com limiar default de 30 dias — por isso uma entrada por commit-base se acumula em `/tmp` e polui o `git worktree list`. Fixamos `audit.cacheMaxAgeDays: 1` no `.fallowrc.jsonc` para varrer, no próximo run, os caches criados há mais de 1 dia; o reuso dentro do mesmo dia contra a mesma base é preservado e o custo de um miss é baixo (`0` desligaria o sweep — não usar).

O débito legado (dead-code em primitivas shadcn, grupos de clones, funções acima do threshold de complexidade) é grandfathered pelo `--gate new-only` — nenhuma dessas linhas precisa ser tocada para o gate passar. Para a contagem atual, rode `npm run fallow`; como na baseline do react-doctor, o número não é fixado aqui de propósito, porque envelhece a cada PR sem que ninguém edite a doc.

O fallow distribui boa parte das suas regras em `warn` por design, para adoção gradual — a doc dele recomenda explicitamente fixá-las em `error` em CI. Como `warn` sai com exit 0, um gate que roda só com os defaults não barra nada nessa faixa: o achado é reportado e o push passa. Daí o bloco `rules` do `.fallowrc.jsonc`, onde 14 dessas regras estão fixadas em `error`, todas com contagem zero de achados no projeto no momento da promoção. O critério de seleção foi o que pode de fato disparar neste stack — com destaque para a família de diretivas client/server (`invalid-client-export`, `misplaced-directive`, `mixed-client-server-barrel`), que é a classe de bug que quebrou três deploys em silêncio (#404) e motivou o CI próprio do #452. Ficaram deliberadamente em `warn` as 5 regras `css-*` (a análise de CSS não produz saída neste projeto — verificado com um token drift deliberado no `globals.css`; promovê-las não protegeria nada e criaria o risco de o CSS legado barrar todo push se uma versão futura passar a emiti-las) e as regras inertes de Vue/Svelte/Angular/SvelteKit e de catálogos pnpm. O raciocínio de cada uma está no próprio `.fallowrc.jsonc`.

Sobre a 3.2.0 (#472) em si: ao contrário do que a leitura apressada do major sugere, ela **não** rebaixou regra alguma. Comparando o mapa `properties.rules.default` dos schemas de 2.104.0 e 3.2.0, o diff completo é a adição de seis regras novas — as 5 `css-*` e `dev-dependencies-in-production` —, todas em `warn`; `coverage-gaps` já era `off` na 2.104.0, e as regras que fixamos em `error` já eram `warn` antes do major. O método vale para o próximo bump: `properties.rules.default` do `schema.json` de cada release é o mapa de severidades, e diffá-lo entre duas versões audita o que mudou sem depender do changelog.

O bloco `rules` só vale enquanto o fallow instalado reconhece cada chave, e a severidade efetiva depende da versão instalada. Três guardas fecham o afrouxamento silencioso (#652). As duas primeiras estão no gate de pre-push (`frontend/scripts/fallow-audit-gate.sh`), que também roda quando o push muda só o `.fallowrc.jsonc`, o `package.json`/`package-lock.json` ou o próprio script; a terceira é uma suíte do Vitest, com hook próprio (`fallow-severity-canary`) para os mesmos arquivos de config:

- **Aviso sobre a config.** Chave renomeada ou removida upstream vira letra morta: o fallow só escreve `unknown rule` no stderr e sai 0. Um `.fallowrc.json` ao lado tem precedência e faz o `.fallowrc.jsonc` ser ignorado inteiro, de novo só com um aviso. O gate roda `fallow config` antes do audit e barra em qualquer linha `WARN` dele. Nome alternativo que o fallow aceita (o plural `mixed-client-server-barrels`, por exemplo) não gera aviso, e nem precisa: a regra continua valendo.
- **Versão instalada ≠ pinada.** Um `node_modules` stale mede com a ferramenta errada; o fallow chegou a ter 2.102.0 instalado com 3.6.0 pinado. A guarda é a mesma do react-doctor, em `frontend/scripts/gates/lib/assert-pinned-version.sh`, e exige pino exato no `package.json`: com `^` ou `~`, o pino não diz qual versão deveria estar instalada.
- **Canário de severidade da família client/server.** `frontend/src/tooling/__tests__/fallow-severity-canary.test.ts` monta um projeto Next temporário com uma violação deliberada por regra (`invalid-client-export`, `misplaced-directive`, `mixed-client-server-barrel`, `unused-server-actions`), roda o `fallow audit --gate all` instalado com o `.fallowrc.jsonc` real e exige exit 1 e cada regra presente com `effective_severity: "error"`. É o único dos três que mede comportamento e não configuração, e por isso pega também o rebaixamento para `warn`. As outras regras fixadas em `error` ficam só com as duas guardas acima: o canário cobre a família que quebrou deploys.

`frontend/.fallowrc.jsonc` (schema oficial do fallow) supressiona os falsos-positivos: `scripts/comentarios-relatorio/**` (`ignorePatterns` — script chamado manualmente via `tsx`, nunca por um entry point do Next) e cada arquivo de primitiva shadcn/Radix em `src/components/ui/` (`ignoreExports`, enumerados um a um — mesmo raciocínio do #230 no react-doctor, ver `docs/LINT_CONFIG.md`). A enumeração é deliberada em vez de um glob `src/components/ui/**`: o diretório também guarda componentes próprios do projeto (`confirm-action-dialog.tsx`, `CopyLinkButton.tsx`) que devem continuar sob checagem normal de dead-code — um glob amplo os esconderia do gate junto com as primitivas geradas. Um terceiro falso-positivo entrou junto com o `error` em `dev-dependencies-in-production`: `ignoreDependencies: ["shadcn", "tailwindcss"]` — eram os dois únicos achados de regra `warn` do projeto, ambos falso-positivo, e sem a supressão a regra em `error` barraria todo push. O raciocínio dos dois está no `.fallowrc.jsonc`.

### typescript-eslint type-checked — os tipos

`typescript-eslint` 8.63.0 (devDependency pinada), via a config dedicada `frontend/eslint.config.typed.mjs` e o script `npm run lint:types`. É separada da config base (`eslint.config.mjs`) e do `npm run lint` rápido porque regras type-checked precisam do `projectService` (carregam o programa de tipos inteiro) e são lentas demais para o lint do dia a dia. O subset é curado de propósito — `no-floating-promises` e `no-misused-promises`, não o `recommendedTypeChecked` inteiro — para mirar o footgun que mais aparece nesta base: promessa async não-tratada em Server Action, hook ou handler de evento.

A escolha se justificou empiricamente: o primeiro scan encontrou 59 errors em cerca de 11 arquivos — promessas não-aguardadas em hooks como `useLlmRunProgress`, `useFieldOrder`, `usePromptPreview`, em componentes como `UserMenu`, `RunLlmButton`, `CopyLinkButton`, `ExportPanel`, e em Server Actions. Eram bugs latentes que o lint sintático não via (ex.: falha de rede silenciosa ao salvar, sem toast nem log). A issue [#378](https://github.com/bdcdo/dataframeitGUI/issues/378) (onda `lint:types` da epic [#376](https://github.com/bdcdo/dataframeitGUI/issues/376)) zerou o débito real (46 errors, 25 arquivos no scan atual): hoje `npm run lint:types` passa com **0 errors** de `no-floating-promises`/`no-misused-promises` no projeto inteiro — o gate de pre-push segue file-scoped por velocidade, mas não há mais débito legado escondido atrás dele.

### typecheck (tsc) — o prerequisito que faltava

O projeto não tinha sequer um script `tsc --noEmit`. O `npm run typecheck` preenche isso e roda no pre-push (projeto inteiro, sem grandfathering — hoje passa com **0 erros**, então qualquer erro de tipo novo barra o push). O compilador nativo em Go (tsgo / TypeScript 7) já está em GA mas ainda não foi adotado, porque o peer do `typescript-eslint` 8 exclui o TS 7 (ver "Monitorar"); ao destravar, basta trocar `tsc` por `tsgo` nesse script.

### Exports de Server Actions — contrato do projeto

O Next.js exige que cada export de valor de um arquivo cuja diretiva é `"use server"` seja uma função `async`; `tsc --noEmit` não detecta essa restrição, e a ausência desse gate causou os três deploys quebrados registrados na [#413](https://github.com/bdcdo/dataframeitGUI/issues/413). A regra local aplicada pelo ESLint permite funções async exportadas diretamente — declaração nomeada, arrow ou function expression em `const`, e default async — e exports exclusivamente de tipo. Valores puros, generators, aliases e reexports de valor ficam bloqueados; a regra não resolve bindings indiretos para manter o gate sintático e file-scoped. Assinaturas de overload e declarações ambientes (`declare function`) passam porque são apagadas na compilação e não exportam valor — a implementação do overload continua sujeita à regra.

Quem aplica a regra é o hook **`lint-types`** (pre-push, arquivos alterados), e não o `npm run lint`, que nenhum hook executa: a regra mora em `eslint.config.mjs` e chega ao hook porque `eslint.config.typed.mjs` faz `...base`. Essa dependência é o único caminho de enforcement — desacoplar as duas configs removeria o gate da #413 em silêncio, sem nenhum teste falhando.

### Carga a frio fora do primeiro teste — contrato da suíte

Com a suíte do Vitest disputando a CPU, o primeiro teste de um arquivo pagava sozinho custos que são do processo, não do teste, e estourava o timeout de 5 s. Duas peças tiram esse custo de dentro dos testes sem mexer no timeout global. A regra local `test-cold-imports/warm-dynamic-imports` (`frontend/eslint-rules/test-cold-imports.mjs`, onde estão o porquê e as exceções) reprova `import()` em tempo de teste cujo módulo não foi carregado antes dos testes, e chega ao pre-push pelo mesmo caminho da regra de Server Actions: `lint-types`, só nos arquivos alterados. O arquivo jsdom cujo primeiro teste estoura por carga a frio de React DOM, Testing Library, user-event e Radix chama `warmUpJsdom()` (`frontend/src/test-utils/jsdom-warm-up.tsx`) num `beforeAll`. A regra local `test-jsdom-warm-up/require-jsdom-warm-up` (`frontend/eslint-rules/test-jsdom-warm-up.mjs`, onde estão o critério e a medição que o sustenta) exige esse `beforeAll` em todo arquivo jsdom que importa `render` da Testing Library. Ela chega ao pre-push pelo `lint-types`, como a anterior, e o comportamento dela se testa em `src/tooling/__tests__/test-jsdom-warm-up.test.ts`, só com a regra. O teste de que ela está ligada no `eslint.config.mjs` fica em `test-cold-imports.test.ts`, que já paga a carga da config; desligá-la da config reprova o vitest. A regra não roda sobre a suíte inteira dentro do vitest: o arquivo que perde o aquecimento ou passa a chamar `render` é um arquivo alterado, e esse o `lint-types` lê. Aplicada à suíte a cada rodada, ela levava 22 s com a suíte em 200% de CPU, e uma segunda carga da config num `beforeAll` estourou os 30 s do hook na mesma faixa. Fica de fora o arquivo que só usa `renderHook`, e por isso a função não é `setupFiles`: nele o aquecimento é custo de CPU sem ganho no primeiro teste. Teste que estoura por outro motivo sob carga aparece em `npm run test:stress -- --quota 300`, e o que estoura por trabalho demais cai no orçamento de CPU da seção seguinte.

### Orçamento de CPU por teste — contrato da suíte

O aquecimento resolve o custo que é do processo. Sobrava o teste que, fora da primeira posição, faz trabalho demais: com a suíte em 200% de CPU, `ComparePage.integration`, `LlmInsightsView`, `EditFieldDialog` e `CodingPage.draft` estouravam os 5 s em rodadas alternadas, e o defeito só aparecia na máquina carregada de quem rodava o pre-push. O `setupFiles` do `frontend/vitest.config.ts` registra, para todo teste, um `beforeEach` e um `afterEach` (`frontend/src/test-utils/cpu-budget.ts`, onde estão a constante e o porquê de cada escolha) que medem a CPU da thread do teste e reprovam o teste que passar de 450 ms. A medida serve porque a CPU do teste muda pouco com a carga (entre a suíte livre e a suíte em 200%, mediana 1,01 e p95 1,17 da razão por teste), enquanto o tempo de parede chega a 8 a 13 vezes a CPU.

O orçamento é um teto, e não uma prova de que o teste aguenta 200%. O número vale para a suíte completa, que é como o pre-push roda: com todos os workers ocupados, o mesmo teste gasta de duas a três vezes a CPU que gasta sozinho, e a conta sobe com a disputa da máquina. Por isso o arquivo que passa isolado pode reprovar no `npm test`, e um teste perto do limite pode passar numa rodada e reprovar na seguinte (p95 de 1,32 vez entre rodadas, para o mesmo teste). Os testes que motivaram a regra gastavam entre 370 e 465 ms na suíte, conforme a carga, e só o pior passava do teto; o que os tirou do timeout foi reduzir o trabalho, até nenhum passar de 350 ms. O alvo de trabalho é 300 ms. Ficam fora da conta, de propósito, o trabalho do `beforeAll`, que é onde o aquecimento mora, e os testes `.concurrent`, que o orçamento recusa porque a CPU da thread de um somaria a do outro.

Quando o orçamento estoura, a saída é tirar trabalho do teste, nunca subir a constante nem o timeout. As causas medidas, em ordem de frequência:

- **Digitação longa.** Cada tecla do `user-event` dispara cinco eventos e re-renderiza o formulário controlado inteiro, uns 10 ms de CPU por caractere com a máquina livre. O teste que só confere o valor final do campo usa `pasteInto` (`frontend/src/test-utils/paste-into.ts`), que entrega o texto num único `input`. Atalho, máscara ou comportamento por tecla continuam com `user.type`.
- **Primeiro clique frio na tela.** Depois do `warmUpJsdom`, o primeiro teste que clica na árvore real ainda paga o JIT dos caminhos da própria tela. Um segundo `beforeAll`, com prazo de 30 s, percorre uma vez o caminho dos primeiros testes (abrir e cancelar, preparar e descartar, confirmar), em que a gravação só chega aos mocks, e desmonta; o `beforeEach` limpa as chamadas e reaplica as implementações que os testes esperam. Há exemplos em `LlmInsightsView.test.tsx`, `ComparePage.integration.test.tsx` e `CompareFilters.test.tsx`.
- **Re-render da árvore inteira a cada interação**, no build de desenvolvimento do React, e o `getComputedStyle` do jsdom 29, que perde o cache de estilo em toda mutação do DOM e é chamado pelas consultas `ByRole` com `name`. Restringir as consultas com `within()` foi medido e não muda o custo de forma mensurável; o que reduz é fazer menos interações por teste.

- **Volume que cresce com a máquina.** O teste que varre arquivos lista pelo git (`git ls-files --cached --others --exclude-standard`), como a varredura de secrets de `supabase-admin-boundary.test.ts`. Percorrer o diretório lia também outras worktrees, saídas de investigação e backups locais, e o custo dependia do que havia em cada checkout.

Para medir: a mensagem do `afterEach` traz a CPU gasta. Para ver todos os testes, `process.threadCpuUsage()` num `setupFiles` extra, gravando por teste, em `vitest run` da suíte completa.

Medição de 2026-11-16, numa VM de 4 vCPUs dividida entre várias sessões, com carga de 5 a 11, sobre os testes de `ComparePage.integration.test.tsx` que reprovaram em rodadas soltas do pre-push (#922):
- **Isolados:** os mais pesados gastaram de 150 a 175 ms de CPU, inclusive com quatro laços ocupando os núcleos.
- **Na suíte completa:** gastaram de 455 a 568 ms, contra o teto de 450. Isso é de 2,6 a 3,7 vezes o isolado, acima das "duas a três vezes" do segundo parágrafo, e passaram ao rodar de novo.
- **O arquivo sozinho, com um worker, em rodadas seguidas:** a soma dos 19 testes variou de 2,5 s a 4,2 s com a carga do momento. Nesta VM, a CPU por teste também acompanha a carga do host, e não só a da suíte.
- **Consulta mais barata:** trocar o `getByRole` com `name` desses testes por uma busca direta nos botões cortou cerca de 16% da CPU do arquivo, menos que a variação acima, e não foi aplicado.

### Locators visíveis nos specs E2E — contrato do projeto

Quando o HTML de uma página com `<Suspense>` termina antes do script `$RC`, o React renderiza a boundary no cliente e o segmento do servidor fica órfão e oculto no fim do body. `getByRole` ignora essa cópia; `getByText`, `getByPlaceholder`, `getByTestId`, `locator(css)` e os demais não, e ela vira strict mode violation ou dobra contagens. Por isso todo locator que parte de um `Page` e não é `getByRole` passa por `visivel()` (`frontend/e2e/visivel.ts`, onde o mecanismo está descrito), e um bloco `no-restricted-syntax` restrito a `e2e/**` em `eslint.config.mjs` barra quem não passar, assim como `getByRole` com `includeHidden: true`.

A exceção é `expect(...).toHaveCount(0)`, que fica sem o filtro para não deixar passar um elemento presente e oculto (o porquê e o caso-limite estão em `visivel.ts`). `page.locator("body")` e `"html"` ficam barrados mesmo dentro de `visivel()`, porque contêm a cópia; os métodos da página que recebem seletor (`page.$$`, `$eval`, `textContent`, `click`, `fill`, `isVisible`, `waitForSelector` etc., lista em `LEGACY_SELECTOR_APIS`, de `frontend/eslint-rules/e2e-visible-locators.mjs`) também.

A regra é sintática: reconhece a página pelo nome (`page` ou `*Page`, direto ou como propriedade, o que cobre `this.page`) e, para que renomear não sirva de saída, exige esse nome em `newPage()`, em `waitForEvent("page"|"popup")`, em parâmetro ou propriedade tipados `Page` (inclusive fixture de `test.extend`) e na desestruturação da fixture. Continuam fora do alcance, por serem raros e caros de pegar sem type-checker: alias (`const p = page`), página tirada de `Promise.all` ou de `context.pages()`, `page.mainFrame()` e `frameLocator`. Locator criado sobre um container achado por `getByRole` (dialog, article) fica livre, porque o container visível não contém a cópia órfã. A aplicação segue o mesmo caminho da regra de Server Actions: hook `lint-types`, via `...base`. O teste `src/tooling/__tests__/e2e-visible-locators.test.ts` roda o ESLint pela config typed, confere que a regra é erro e não aviso, cobre um módulo de apoio fora de `*.spec.ts` e relinta a pasta `e2e/` inteira, de modo que afrouxar a regra sem mexer nos specs, ou desacoplar as duas configs, reprova no Vitest.

### ruff — lint, format e complexidade do backend

`ruff` (dependency-group dev em `backend/pyproject.toml`), via hooks locais `ruff-check` e `ruff-format` que rodam `uv run --project backend ruff` — a versão é a travada em `backend/uv.lock`, pino único da ferramenta (não repetir o número aqui: o comentário desatualiza sozinho, foi o que aconteceu entre o #513 e o #530). Por que não o hook oficial `astral-sh/ruff-pre-commit`: comentário do hook em `.pre-commit-config.yaml` (#554). Cobre o backend Python, que não tinha nenhum gate. Resolve o eixo de complexidade que a #260 levantou (a pergunta original era sobre o `lizard`): no frontend a complexidade já está coberta por react-doctor + fallow, então a lacuna real era o Python, e o `ruff` entrega `C901` (mccabe) junto com lint (E/F/I/B) e format num binário só — mais que o `lizard`, que só mede CCN.

Config em `backend/pyproject.toml`: `select = ["E", "F", "I", "B", "C901"]`, `ignore = ["E501"]` (comprimento de linha fica a cargo do `ruff format`), `max-complexity = 10`. Os hooks rodam file-scoped (só os `.py` alterados), com `--fix` no lint, então o débito legado fica grandfathered por arquivo-tocado.

**Atualização (#376, 2026-07):** dos 8 achados auto-fixáveis e 16 arquivos pendentes de format do baseline original, só restavam 10 arquivos pendentes de format no momento da #376 (o lint já estava zerado por trabalho anterior não documentado) — resolvidos com `ruff format .`. Das três funções originalmente isentas de `C901` via `per-file-ignores`, duas foram refatoradas e removidas da isenção:

- **`evaluate_condition`** (era 13): extraída em dispatch dict por operador (`equals`/`not_equals`/`in`/`not_in`/`exists`), cada ramo virou uma função auxiliar de baixa complexidade.
- **`compile_pydantic`** (era 20): o loop de normalização de metadata pós-modelo (help_text, subfield_rule, allow_other, condition, justification_prompt, sufixos de description) foi extraído em funções auxiliares (`extract_json_schema_extra`, `_resolve_field_type_and_options`, `_strip_description_suffixes`, `_assemble_field_dict`, `_build_field_dict`). A allowlist de segurança AST (`build_model_from_code`/`_reject_dangerous`/`_resolve_type`) não foi tocada.

Ao remover a isenção de arquivo inteiro de `pydantic_compiler.py`, o gate revelou que **duas funções da própria allowlist de segurança também excediam o limite** — `_reject_dangerous` (14) e `_resolve_type` (12) — escondidas até então pelo `per-file-ignores` de arquivo inteiro. São isentas agora via `# noqa: C901` inline (não mais `per-file-ignores`), pela mesma cautela nas duas mas por motivos técnicos distintos (documentados no docstring de cada uma): `_reject_dangerous` é um único `ast.walk` cujos `if`s são checagens de allowlist independentes — decompor não fragmentaria o walk, mas é código de segurança e um refactor apressado arrisca introduzir uma brecha sem reduzir risco real; `_resolve_type` é dispatch recursivo (sem um `ast.walk` central), e alguns ramos poderiam em tese virar funções auxiliares, mas a mesma cautela de segurança se aplica. A suppression pontual por linha, em vez de isenção de arquivo inteiro, é a melhoria real aqui — qualquer *nova* função complexa em `pydantic_compiler.py` volta a disparar `C901` normalmente.

**Correção de uma revisão do PR #379 (2026-07-03):** a extração de `evaluate_condition`/`compile_pydantic` introduziu duas duplicações, corrigidas no mesmo PR. Primeiro, o guard de normalização de `json_schema_extra` (callable/isinstance-dict/default-`{}`) existia de forma independente em três lugares (`condition_evaluator.py`, `pydantic_compiler.py`, `llm_runner.py`); consolidado no único helper público `pydantic_compiler.extract_json_schema_extra`. Segundo, a lista de operadores de condição (`equals`/`not_equals`/`in`/`not_in`/`exists`) tinha duas cópias independentes (`_CONDITION_OPS` em `pydantic_compiler.py` e o novo `_CONDITION_HANDLERS` em `condition_evaluator.py`); a primeira virou a constante pública `CONDITION_OPERATORS`, e o dispatch de `condition_evaluator.py` deriva sua ordem dela.

**Atualização (#377, 2026-07):** `run_llm` deixou de precisar de isenção C901. O PR #398 criou o teste de integração direto (`backend/tests/test_llm_runner_run_llm.py`) e extraiu o laço de pós-processamento/salvamento por linha para `_process_and_save_rows`; a continuação da #377 completou a decomposição em helpers de preparação de modelo, normalização de kwargs, carregamento de documentos, execução em batches, transformação por linha e verificação de run comprometida. Com isso, `uv run ruff check .` passa sem `[tool.ruff.lint.per-file-ignores]` para `services/llm_runner.py`.

### backend-pytest — a suíte do backend como gate

Enquanto o `ruff` cobre o eixo estático do Python, ele não roda os testes — a suíte de auth que o #195 adicionou (`backend/tests/`) não gateava nada, então uma regressão que enfraquecesse o gate JWT ou quebrasse as fronteiras 401/403/404/503 mergearia com o gate verde e o deploy do Fly shipparia direto para produção (issue #337). O hook local `backend-pytest` fecha essa lacuna: roda `uv run pytest -q` (working-dir `backend/`) no estágio de pre-push sempre que o push toca código Python ou os arquivos que definem o grafo e a imagem do backend (`pyproject.toml`, `uv.lock`, `Dockerfile`, `.dockerignore` e `docker-compose.yml`). Diferente dos hooks file-scoped, roda a suíte inteira — testes não têm noção de "linha grandfathered". Diferente do semgrep (fail-open em erro de infra), é **fail-closed**: se o `uv` não estiver no PATH o push é barrado com mensagem, porque é um gate de verdade, não um sinal informativo. `[tool.uv] package = false` no `backend/pyproject.toml` faz o `uv run` não tentar empacotar o app (que é um FastAPI flat, não uma lib instalável), evitando a regressão histórica de build. Cada teste tem um teto de 60 s (`pytest-timeout`, `timeout = 60` e `timeout_method = "thread"` no `[tool.pytest.ini_options]`, #833): um deadlock ou espera infinita reprova com a pilha de todas as threads em vez de pendurar o push. O método `thread` encerra a sessão inteira no primeiro timeout, então os testes seguintes não rodam naquela execução; teste que precise de mais tempo declara `@pytest.mark.timeout(n)`, e `--timeout=0` desliga o teto numa depuração local. Desde o #649 a suíte também roda no servidor, como célula do `ci.yml`. A decisão anterior, de manter o gate pré-merge só nos hooks locais, apoiava-se numa premissa falsa ("sem branch protection no free tier"): o repositório é público, e branch protection e rulesets são gratuitos em repositório público. Nenhum dos dois está ligado, então hoje um job de Actions vermelho aparece no PR mas não bloqueia o merge; ligar o ruleset com o `ci-required` é a [#651](https://github.com/bdcdo/dataframeitGUI/issues/651).

### db-tests (test:db) — as suítes de contrato SQL como gate

As suítes de contrato do banco (`frontend/supabase/tests/*.sql`) — RLS, RPCs atômicas, arquivamento por triggers, serialização com dblink — não rodavam em nenhum hook nem no CI. O `test:db` era um `&&` encadeado que dependia de alguém lembrar de rodar, e o `&&` fazia a primeira falha esconder as demais: quatro suítes ficaram vermelhas na `main` sem ninguém ver (issue [#557](https://github.com/bdcdo/dataframeitGUI/issues/557)). O hook `db-tests` fecha essa lacuna, no mesmo padrão fail-closed do `backend-pytest`.

Duas peças: (1) o runner `frontend/scripts/run-db-tests.sh` substitui o `&&` por uma varredura que roda **todas** as suítes, reporta `PASS`/`FALHOU` por suíte e sai `!=0` se qualquer suíte de **gate** falhar — nunca para na primeira; (2) o hook de pre-push chama o runner quando o push toca migrations, suites `.sql` ou os próprios scripts do runner (`files:` scoped). O `database-tests.yml` roda o mesmo runner no CI, e não uma lista própria de suítes: a lista à mão de antes tinha ficado 17 suítes atrás dos conjuntos do runner. No GitHub Actions o runner abre um grupo por suíte, antes de rodá-la e com a saída inteira, e anota a suíte de gate que falha. Além das suítes SQL, o runner roda o contrato payload×schema dos writes do `llm_runner` em `llm_runs` (`backend/tests/integration/`, `pytest -m integration` com `supabase.Client` real, via `scripts/run-backend-integration.sh`), porque o `_FakeTable` dos testes unitários aceita qualquer chave de payload e deixou `llm_runs.round_id` 11 dias sem coluna ([#673](https://github.com/bdcdo/dataframeitGUI/issues/673), [#674](https://github.com/bdcdo/dataframeitGUI/issues/674)); esse contrato também tem hook próprio de pre-push (`llm-runs-contract`), que dispara quando o push toca `backend/services/llm_runner.py` ou esses testes sem rodar a bateria SQL, e o `database-tests.yml` roda em todo PR, chamado pelo job `database` do `ci.yml`. É **fail-closed**: sem o Supabase local no ar, o runner falha com mensagem (`npx supabase start`), porque é um gate de verdade — não um sinal informativo.

O runner separa dois conjuntos, e a distinção é a fonte única de verdade de quem gateia: `GATE_SUITES` e `PGTAP_SUITES` derrubam o exit (entre as de gate estão as órfãs da #557 que passam, `auto_review_reconciliation_outbox`, `schema_revision_rpcs`, consertada na [#571](https://github.com/bdcdo/dataframeitGUI/issues/571), e `schema_revision_serialization`, consertada na [#572](https://github.com/bdcdo/dataframeitGUI/issues/572)); `KNOWN_RED` é a suíte vermelha rastreada em issue própria — hoje vazia: a última, `value_equivalences` ([#913](https://github.com/bdcdo/dataframeitGUI/issues/913), exige superusuário), passou a gate ao conectar como `supabase_admin` pela diretiva `-- @test-role: supabase_admin` (#650) que o `run-sql-test.sh` lê da própria suíte. Uma suíte em `KNOWN_RED` roda e é **reportada** como `RED*` com a issue, mas não bloqueia até ser consertada — não é silenciamento, aparece no resumo a cada execução, e ao ficar verde move-se de `KNOWN_RED` para `GATE_SUITES`. Se for necessário empurrar com o Supabase fora do ar, o bypass é explícito: `SKIP=db-tests git push`.

Quatro guardas no runner fecham os modos de drift que originaram ou disfarçariam a #557. Primeiro, **drift disco↔runner**: a causa raiz da #557 foi uma suíte `.test.sql` fora de toda cadeia, então o runner compara o glob `supabase/tests/*.test.sql` contra a união dos três conjuntos e recusa (exit `!=0`, antes de rodar) qualquer arquivo não classificado — ou qualquer suíte listada sem arquivo no disco. O estado "suíte fora do gate" deixa de ser representável em vez de apenas improvável. Segundo, **promoção forçada**: quando uma `KNOWN_RED` passa a passar, o gate falha pedindo que ela seja movida para `GATE_SUITES` — a exceção não apodrece silenciosamente até alguém reparar. Terceiro, **diagnóstico em falha**: a saída de cada suíte vai para um log temporário e a cauda é impressa no `FAIL` de gate, sem exigir re-run da suíte (`npm run test:db -- <suíte>` roda só as nomeadas). Quarto, **exceção com dono** (#650): toda entrada de `KNOWN_RED` aponta para uma issue (`#N`) e a issue precisa estar aberta (`gh issue view`); com a issue fechada ou inexistente, ou sem `#N`, o runner recusa antes de rodar. Fora do CI a consulta é fail-open: sem `gh`, sem rede ou sem login, avisa e segue. No CI o `gh` usa o token do workflow, e a consulta que falha reprova. Uma ressalva de escopo: o gate cobre o **eixo SQL** (migrations, suítes, scripts do runner) por `files:`, mais o `llm_runner` do backend pelo `llm-runs-contract`; uma mudança em código de aplicação que altere o contrato de uma RPC — por exemplo `src/actions/field-reviews.ts` — **não** dispara `db-tests`, e a suíte de contrato correspondente só a pega se o mesmo push também tocar o SQL.

### e2e-smoke (Playwright) — o gate de fluxos autenticados, e por que MCP/browser não substitui

`@playwright/test` (devDependency), 4 specs ativos em `frontend/e2e/*.smoke.spec.ts` (`dashboard.smoke`, `config-guard.smoke`, `export.smoke`, `lottery.smoke`), config em `frontend/playwright.config.ts`. A autenticação usa Clerk Testing Tokens por ticket (`@clerk/testing`) em vez de UI ou senha — resolve, na íntegra, o problema levantado na issue [#107](https://github.com/bdcdo/dataframeitGUI/issues/107): sem essa peça, qualquer agent/CI que tentasse validar um fluxo logado travava no redirect para `accounts.dev`, o domínio de login do Clerk, sem forma documentada de gerar sessão sem passar pela UI.

Até a issue [#306](https://github.com/bdcdo/dataframeitGUI/issues/306), essa suíte existia mas não rodava sozinha — só quando alguém lembrava de digitar `npm run test:e2e`. O hook `e2e-smoke` fecha essa lacuna: roda no pre-push, no mesmo padrão dos outros hooks pesados, e no modo `PLAYWRIGHT_PRE_PUSH=1` falha fechado se faltarem as variáveis obrigatórias de Supabase, Clerk ou E2E. A fonte canônica do contrato são as atribuições não comentadas de `frontend/.env.local.example` e `frontend/.env.e2e.example`; o preflight lê esses arquivos diretamente, em vez de manter uma lista paralela. Atribuições comentadas são opcionais: `E2E_MASTER_EMAIL`, por exemplo, habilita o caso de master no dashboard, mas sua ausência não invalida os demais specs ativos do gate. O modo manual `npm run test:e2e` continua permissivo: os specs fazem `test.skip()` quando faltam usuários/projetos de teste, para permitir inspeção parcial em checkouts sem fixture completa. Se for necessário empurrar sem uma credencial obrigatória, o bypass deve ser explícito: `SKIP=e2e-smoke git push`.

O hook seta `PLAYWRIGHT_PRE_PUSH=1`, que `playwright.config.ts` usa para desviar do comportamento "modo dev" em quatro pontos: por default, quando `E2E_BASE_URL` não está definido, o `baseURL` muda para `http://localhost:3100`; `webServer.reuseExistingServer` vira `false`; `workers` vira `1`; e o servidor passa a ser o build de produção (`npm run build && npm run start`) em vez do `next dev`. Um `E2E_BASE_URL` explícito sobrescreve esse default e a porta repassada ao servidor acompanha a porta dessa URL.

O build de produção existe porque o `next dev` atende requests antes de conhecer todas as rotas: elas entram na tabela à medida que a varredura do app dir avança, e com a máquina carregada essa varredura leva segundos. A request que chega antes recebe o 404 embutido do Next, sem nenhum erro no log, e o spec falha acusando o fixture. Em outubro de 2026 isso derrubou 13 de 16 testes de uma rodada, todos em rotas de `/projects/[id]`, enquanto o `/dashboard` passava. O `next start` lê as rotas do manifesto do build e não depende da varredura; ele também elimina a compilação sob demanda, que estourava o timeout de `page.goto` com load alto. O custo é o `next build` antes da suíte, cerca de 50 s com load 60, que inclui uma segunda checagem de TypeScript além do hook `typecheck`.

Quando um spec falha, o `test` de `frontend/e2e/base-test.ts` (que todo spec importa, direto ou via `fixture-lock-test.ts`; o gate é `e2e-base-test-coverage.test.ts`) imprime cada navegação com erro e classifica os 404: rota não casada pelo servidor, `notFound()` do app ou `auth.protect()` do Clerk. A classificação lê a raiz da árvore de segmentos do payload RSC, que existe nos dois modos; a regra está em `frontend/e2e/navigation-diagnostics.ts`. A porta dedicada evita colidir com o `npm run dev` interativo em `3000`, e `workers: 1` evita reintroduzir entre arquivos o burst de `clerk.signIn()` contra o tenant dev que a #198/PR #294 corrigiu dentro de um arquivo. Nenhuma dessas mudanças afeta o modo manual, que continua otimizado para iteração local.

A porta dedicada é a mesma em toda worktree, então dois pushes ao mesmo tempo em worktrees diferentes disputavam a 3100 e o segundo morria em "already used". Por isso o hook roda o Playwright dentro de `frontend/scripts/e2e-lock.sh`, uma trava `flock` de máquina num arquivo fora do repositório (`~/.cache/dataframeitGUI/pre-push-e2e.lock` por default, comum a toda worktree e todo clone do mesmo usuário), que serializa os pushes e dura enquanto durar o Playwright, mesmo quando o hook recebe SIGTERM ou SIGHUP. Quem chega depois espera até `E2E_LOCK_WAIT_SECONDS` (default 1800), com um aviso que nomeia a worktree dona da trava, e falha com essa mesma informação se o teto estourar. Serializar foi preferido a dar uma porta a cada worktree porque evita também somar a carga de duas suítes e os logins de duas execuções contra o tenant dev do Clerk. A trava não é a proteção do projeto fixture do Supabase remoto: essa é o lock por projeto que os specs que mutam o banco tomam dentro de cada teste (`holdFixtureLock`), que vale também para `npm run test:e2e`, `--ui` e `npx playwright test` direto, que não passam pela trava. Os dois não formam ciclo, porque a trava é pedida antes de qualquer teste começar e ninguém a pede segurando o lock por projeto. Nenhum dos dois cobre outra máquina nem agente na nuvem com o mesmo `.env.e2e`.

Isso também responde à pergunta que motivou a #306: dá pra confiar em MCP/automação de browser (ex.: Claude no Chrome) em vez de manter essa suíte? Não — são complementares, não substitutos. Uma sessão de browser interativa bateria exatamente na mesma parede de login do Clerk que o #107 resolveu com Testing Tokens, a menos que um humano autentique manualmente a cada sessão; e diferente de um spec versionado, cada sessão de MCP é efêmera — não fica um artefato de regressão que rode desacompanhado no próximo push. O papel do MCP/browser continua sendo a verificação pontual de uma mudança específica durante o desenvolvimento (o comportamento default do Claude Code para mudanças de UI), não a rede de regressão automatizada — essa é a suíte Playwright.

A cobertura de hoje é deliberadamente rasa (4 specs de fumaça, focados nos fluxos sensíveis a auth/RLS que motivaram o #107 originalmente) — expandi-la é trabalho incremental, fora do escopo da #306, e cabe melhor como issues pontuais por fluxo do que como uma expansão única.

### mypy — o eixo de tipos do backend

`mypy` (dependency-group dev em `backend/pyproject.toml`, `>=2.2.0`), via hook local de pre-push, escopado aos `.py` alterados (mesmo padrão do `lint-types` do frontend). Fecha a lacuna que o `ruff` deixa: `ruff` cobre lint/format/complexidade, mas não checa tipos — o backend é o boundary de segurança internet-facing (pós-#195/#337) e um `Any` vazando de um `dict` cru do LLM até um argumento tipado é exatamente o footgun que motivou o `no-floating-promises` no frontend, só que do lado dos tipos.

Config em `backend/pyproject.toml`: `ignore_missing_imports = true` (as libs de LLM — `langchain-*`, `dataframeit` — não publicam stubs; sem isso todo `import-untyped` mascararia os erros reais) e sem `strict` de cara, mesmo raciocínio do subset curado do `lint:types` no frontend. `python_version = "3.12"` casa com o runtime real (Dockerfile e `.venv`), não com o piso `requires-python = ">=3.11"` — simular 3.11 faz o mypy recusar parsear sintaxe 3.12+ em stubs de terceiros (ex.: `type` statement do PEP 695 no stub do `numpy`) e abortar em vez de reportar um erro de tipo normal.

`follow_imports = "silent"` é o que faz o grandfathering file-scoped funcionar de fato: sem ele, checar um único arquivo (como o hook de pre-push faz) também reporta erros de qualquer módulo que esse arquivo importe — como `services/auth.py` é importado por praticamente toda rota, qualquer push que tocasse `routes/llm_routes.py` (por exemplo) bloquearia pelos erros legados de `auth.py`, mesmo sem editá-lo. Com `silent`, o módulo importado continua sendo checado (a inferência de tipo permanece correta) mas seus diagnósticos ficam suprimidos quando ele não é o alvo explícito do comando.

`exclude = ["tests/"]` só tem efeito no modo de descoberta de projeto (`uv run mypy .`); é ignorado quando arquivos são passados explicitamente, que é como o hook invoca o mypy. A proteção real de `tests/` no hook vem do `exclude: ^backend/tests/.*\.py$` em `.pre-commit-config.yaml` — os dois precisam ficar em sincronia manualmente, não há enforcement cruzado entre eles.

O primeiro scan completo encontrou **113 erros em 5 arquivos**, com **103 (91%) concentrados em `services/llm_runner.py`** — quase todos `union-attr`/`arg-type` da explosão do alias `JSON` recursivo (`int | float | Sequence[JSON] | Mapping[str, JSON] | None`) toda vez que um `dict` cru vindo do LLM é acessado. A #377 removeu a isenção `C901` ao decompor o fluxo de controle de `run_llm`, mas essa decomposição não estreitou os tipos recursivos vindos do LLM. Por isso `services/llm_runner.py` continua isento apenas no mypy, via `[[tool.mypy.overrides]]` (`ignore_errors = true`); remover essa isenção exige um trabalho próprio de tipagem e, sem ele, qualquer push que tocasse o arquivo bloquearia nos 103 erros pré-existentes, já que o hook é file-scoped (não line-scoped). Os 10 erros restantes em 4 arquivos (`services/auth.py`: 4, `routes/pydantic_routes.py`: 4, `services/pydantic_compiler.py`: 1, `main.py`: 1), inicialmente grandfathered pelo escopo file-a-file do hook, foram corrigidos na issue [#380](https://github.com/bdcdo/dataframeitGUI/issues/380) — `uv run mypy .` roda limpo hoje, com exceção de `services/llm_runner.py`.

### React Scan — o runtime

`react-scan` 0.5.7 (devDependency pinada), via `npm run scan` contra a aplicação em dev. É o eixo que o react-doctor estático não alcança: detecta re-renders desnecessários ao vivo. Casa com a dívida de performance da plataforma (diagnosticar e corrigir a lentidão atual). É ferramenta de diagnóstico pontual, não gate — roda quando se investiga performance, não em CI.

### Dependabot e semgrep — a segurança

Sobre o gitleaks (secrets) que já existia, a #260 acrescentou duas camadas. O **Dependabot** (`.github/dependabot.yml`) cobre dependências vulneráveis e desatualizadas em npm (`/frontend`), uv (`/backend` e `/.github/ci-tools`, o pre-commit do CI), github-actions e pre-commit: roda no servidor do GitHub e abre PRs sozinho, com `cooldown` de 7 dias antes de propor uma versão recém-publicada — janela de defesa contra supply-chain. O **semgrep** (hook de pre-push via `uvx`, rulesets `p/typescript`, `p/react`, `p/python`) faz SAST de código inseguro em JS/TS e Python, complementando as poucas regras de Security do react-doctor. O `--baseline-commit` limita aos achados novos vs `origin/main` (grandfathering); o hook falha fechado em achado real (exit 1) e falha aberto em erro de infra/rede (exit > 1), para não travar um push offline. No CI o mesmo script (`frontend/scripts/semgrep-gate.sh`) roda com `GATE_FAIL_OPEN=0`: tenta mais duas vezes e reprova, porque no servidor um semgrep que não rodou não pode passar por verde.

### CI (`ci.yml`) — os gates de pre-push no servidor

Os hooks locais não rodam para quem usa `--no-verify`, `SKIP=`, edita pela web ou não rodou `pre-commit install`, e PR do Dependabot nunca passa por eles. O `.github/workflows/ci.yml` roda os mesmos hooks no servidor em todo PR e em todo push na `main`, sem segredo e sem deploy ([#649](https://github.com/bdcdo/dataframeitGUI/issues/649)).

A matriz não é escrita no workflow. O job `discover` chama `.github/scripts/ci-gate-matrix.sh`, que lê o `.pre-commit-config.yaml` e emite uma célula por hook com `pre-push` nos stages; cada célula roda `pre-commit run --hook-stage pre-push --all-files <id>`. Hook novo de pre-push vira célula sem tocar no `ci.yml`: a lista de gates do servidor não tem como ficar atrás da lista local, que foi como suítes inteiras ficaram fora de todo gate. Três arquivos declaram o que foge disso, e o teste de contrato `.github/scripts/test-ci-gate-matrix.sh` (hook `ci-gate-matrix` e primeiro passo do `discover`) reprova a declaração que deixou de valer:

- `.github/ci-exempt-gates.json`: hook que não pode rodar no servidor, com motivo obrigatório. Chave que não corresponde a hook de pre-commit nem de pre-push (órfã) ou motivo vazio reprovam. Os motivos de cada uma ficam no próprio arquivo.
- `.github/ci-gate-shards.json`: hook dividido em fatias, que recebe a fatia em `GATE_SHARD`.
- `GATE_FAIL_OPEN=0`, que toda célula recebe: o gate que no push local libera em erro de infra (semgrep) reprova no servidor. É variável do mesmo script, e não um segundo script.

O CI mede estado absoluto e o hook mede o delta: com `--all-files`, `lint-types` e `mypy` rodam em todo arquivo que o `files:` do hook casa (o `mypy` segue sem `backend/tests/`), e os hooks com `files:` rodam mesmo quando o PR não toca o que eles observam. `fallow-audit` e `semgrep` seguem medindo o que o PR introduz contra `origin/main`. O job `lint` roda o estágio pre-commit inteiro numa chamada (`pre-commit run --hook-stage pre-commit --all-files`), com as exceções do mesmo `ci-exempt-gates.json` em `SKIP`, e o eslint, que não tem hook. Uma chamada, e não uma célula por hook, porque são leves e cada célula monta o ambiente inteiro; hook novo de pre-commit entra sozinho do mesmo jeito. O `gitleaks` e o `react-doctor` são as exceções desse estágio: os dois medem o diff local (staged, linhas alteradas), que no servidor é vazio. O gitleaks roda no `secret-scan.yml`, e o react-doctor é rede local por decisão (`docs/LINT_CONFIG.md`).

O banco entra pelo job `database`, que chama o `database-tests.yml` (`workflow_call`) em todo PR, com o Supabase local em Docker e o mesmo runner do hook `db-tests`. O filtro de `paths` que o workflow tinha o deixava fora do `ci-required`, e a lista de caminhos era mantida à mão. O custo é rodar o banco (cerca de 4 minutos, em paralelo com as células) também no PR que não toca nele.

O pre-commit que o `ci.yml` roda vem de `.github/ci-tools/` (`uv run --locked --project .github/ci-tools pre-commit`), um projeto uv só com ele, que o Dependabot de `uv` atualiza pelo `uv.lock` ao lado. Fica fora do `backend/uv.lock` porque o virtualenv que o pre-commit puxa subiria o `packaging` da imagem de produção. O `test_toolchain_pins.py` reprova a versão escrita à mão no workflow.

`ci-required` espera todos os jobs com `if: always()` e exige `success` de cada um. É o único check a marcar como obrigatório no ruleset ([#651](https://github.com/bdcdo/dataframeitGUI/issues/651)): uma lista de checks na UI do GitHub seria mais uma lista à mão. Por isso o workflow não tem filtro de `paths`: workflow que não dispara deixa o check obrigatório em "Expected" para sempre, e o PR trava sem nada vermelho para consertar. O teste de contrato barra a volta do filtro e o job que fique fora do `ci-required`.

### PR que sobe ferramenta de gate: medição pareada antes do merge

O Dependabot também sobe o pino de ferramentas que são gate. No ecossistema `pre-commit`, sobe o `rev` de `pre-commit-hooks`, `gitleaks` e `actionlint`. No `uv`, sobe o `ruff` e o `mypy` do `backend/uv.lock`, que são as versões rodadas pelos hooks (#554). No `npm`, sobe react-doctor, fallow e typescript-eslint, dentro do grupo `frontend-minor-patch`. A versão nova pode mudar a contagem de achados **na mesma árvore**, sem que nenhuma linha nossa mude. O risco já foi medido aqui: no #534, o react-doctor foi de 1 para 10 errors só ao subir de 0.7.3 para 0.7.8 (ver `docs/LINT_CONFIG.md`). O verde do PR não mede esse efeito, porque o PR só toca o pino, os hooks são file-scoped ou new-only e o do gitleaks lê só o diff staged.

Por isso, antes do merge, todo PR que sobe uma ferramenta de gate exige três passos:

1. **Medir a versão antiga e a nova sobre a mesma árvore** e comparar as contagens.
2. **Registrar no corpo do PR** o comando, a contagem em cada versão e o que mudou.
3. **Se a contagem subir, decidir de forma explícita**: corrigir os achados novos no próprio PR ou suprimi-los pontualmente com o porquê ao lado, no padrão que já existe (allowlist comentada em `.gitleaks.toml`, `-ignore` comentado no hook do actionlint, `# noqa` inline no ruff, `docs/LINT_CONFIG.md` no react-doctor). Não se mergeia sem nomear a diferença.

Como medir, no worktree do PR: `bash frontend/scripts/measure-gate-bump.sh [pre-commit|uv] [base]`. A versão antiga é a que a config ou o lockfile do merge-base (`git merge-base origin/main HEAD`, ou a `base` passada) fixa, e a nova é a do HEAD. O script mede o HEAD e para se houver mudança não commitada em arquivo versionado. Ele imprime a saída de cada ferramenta nas duas versões e um resumo no fim (hook ausente na config de um lado aparece como ausente, e não como exit 1), e o teste dele fica em `frontend/src/tooling/__tests__/measure-gate-bump.test.ts`.

- `pre-commit`: `check-merge-conflict` e `actionlint` com a `.pre-commit-config.yaml` de cada lado, e o gitleaks com o `rev` de cada lado.
- `uv`: `ruff check --statistics`, `ruff format --check` e `mypy` no `backend/`, com o `uv.lock` e a config (`[tool.ruff]`, `[tool.mypy]` do `pyproject.toml`) de cada lado, tirados de um projeto temporário. São comandos só de leitura, fora do hook, que roda o ruff com `--fix`, e sem cache no worktree.

O gitleaks é a exceção entre os hooks. O hook roda `gitleaks git --pre-commit --staged` e ignora a lista de arquivos, então `pre-commit run gitleaks --all-files` passa sem escanear nada ("scanned ~0 bytes"). Ele continua assim, porque no commit é o diff staged que importa. O script mede a árvore com `gitleaks dir`, trocando o entry do hook, sobre uma cópia só dos arquivos versionados (`git archive HEAD`, então `.venv`, `node_modules` e `.env.local` ficam fora). Na cópia ele planta um token canário gerado na hora: se o canário não aparece no relatório, a varredura não leu a árvore e o script falha, em vez de registrar "0 achados".

O `npm` fica fora do script, e a troca é à mão: `frontend/package.json` e `frontend/package-lock.json` do merge-base, `npm ci` e o comando completo da ferramenta (o scan completo de `docs/LINT_CONFIG.md`, `npm run fallow`, `npm run lint:types`), depois o mesmo na head do PR. No fallow, compare também a severidade das regras entre os `schema.json` das duas versões (seção do fallow, acima): regra que sobe para `error` muda o gate sem mudar a contagem.

## Setup (uma vez por checkout)

```bash
cd frontend && npm install            # instala fallow, typescript-eslint, react-scan
uv tool install pre-commit            # se ainda nao tiver
pre-commit install                    # instala os hooks de pre-commit E pre-push
```

A partir daí os gates rodam sozinhos. Comandos manuais (para debug ou inspeção) ficam documentados, mas não são necessários no dia a dia:

```bash
cd frontend
npm run typecheck        # tsc --noEmit
npm run lint:types       # typescript-eslint type-checked (projeto inteiro)
npm run fallow           # scan completo (dead-code + dupes + health)
npm run fallow:audit     # gate incremental (new-only vs origin/main)
npm run scan             # React Scan (precisa de `npm run dev` rodando)

cd backend
uv run ruff check .      # lint (ruff do dev-group via uv.lock, o mesmo do hook)
uv run ruff format .     # format
uv run mypy .            # type-check (llm_runner.py isento; ver seção mypy acima)
```

## Monitorar

- **tsgo / TypeScript 7 (Project Corsa)** — compilador nativo em Go, ~10× mais rápido, **já em GA** (a `latest` no npm é a 7.0.2). Ainda assim não adotado, por dois motivos que se somam: a API programática só entra na 7.1, que ainda não saiu como estável (só builds `dev`), então `typescript-eslint`/`ts-morph` não rodam sobre o nativo; e o `typescript-eslint` 8 declara peer que exclui o TS 7, de modo que instalar a 7 é exatamente o que o pin abaixo impede. Trocar `tsc` por `tsgo` no script `typecheck` segue sendo um drop-in em si, mas está **bloqueado pela mesma condição de destrave do pin** — não pelo calendário do GA, que já passou. O agente também pode chamar o MCP/skill do fallow e os findings do semgrep guardian sob demanda.

  Por isso o TypeScript fica pinado em `~6.0` no `frontend/package.json`: o `typescript-eslint` 8.63.0 declara peer `typescript: >=4.8.4 <6.1.0` — o teto é **6.1, não 7**, fronteira minor (hoje a última 6.x publicada é a 6.0.3). A trava é dupla e simétrica, porque os caminhos de violação são dois e independentes. Primeiro, o `~6.0` barra o `npm install`: uma faixa `^6` deixaria a 6.1 entrar sozinha em qualquer refresh de lockfile, sem diff no `package.json`. Segundo, o `ignore` de **minor+major** no `.github/dependabot.yml` barra o Dependabot, que sob o `versioning-strategy` default `auto` elevaria a faixa para `~6.1` num PR do grupo `frontend-minor-patch` — 6.0.3→6.1.0 é `semver-minor`, então um ignore só de major não pegaria. A 6.0.x segue fluindo normalmente. A condição de destrave é o `typescript-eslint` 9 com suporte a TS 7 — aí saem juntos a faixa, o ignore e o bloqueio do tsgo.

## Avaliadas e diferidas

- **lizard** (complexidade ciclomática portável) — redundante no frontend (react-doctor + fallow já cobrem) e mais raso que o `ruff` no backend (só mede CCN, não faz lint). Coberto pelo `ruff`.
- **Biome** (lint+format all-in-one) — sobreporia o investimento já feito em ESLint + react-doctor.
- **type-coverage** — o projeto já é `strict`; ganho marginal fora de migração/caça a `any`.
- **Analisadores de bundle** (vite-bundle-visualizer, source-map-explorer) — só se performance de bundle pesar; a dívida de performance atual não é de bundle.
